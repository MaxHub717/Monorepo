Development — Competition Model Migration

## Old Schema/API → Phase / Plot / Series / Game

**Status:** Canonical Development Mapping
**Applies to:** NGL Competition & Scheduling Engine v2
**Purpose:** Define how the existing league implementation maps to the new competition model and identify what is retained, transformed, deprecated, or replaced.

---

# 1. Purpose

The current NGL implementation was built around:

```text
Season
└── Division
    ├── DivisionParticipant
    ├── MatchWeek
    ├── Fixture
    │   └── Match
    │       └── MatchResult
    └── StandingsRow
```

The new competition model is:

```text
Season
└── Phase
    └── Plot
        └── Series
            ├── Game 1
            ├── Game 2
            └── Game 3
                 ↓
              Result
                 ↓
            Advancement
```

The new model treats the **Series** as the competitive and scheduling unit.

A Fixture is no longer the primary competition object.

A Match is no longer the container for the complete player-v-player competition.

A Series contains exactly three Games, and the Series determines advancement.

# 3. Canonical Target Domain

The target hierarchy is:

```text
Season
│
├── SeasonRuleset
│
├── Division
│
└── Competition
    │
    ├── Phase 1
    │   ├── Plot 1
    │   │   ├── Series
    │   │   │   ├── Game 1
    │   │   │   ├── Game 2
    │   │   │   └── Game 3
    │   │   └── Series
    │   └── Plot 2
    │
    ├── Phase 2
    │   ├── Plot 1
    │   └── Plot 2
    │
    └── ...
```

The competition hierarchy is therefore:

```text
Season
→ Phase
→ Plot
→ Series
→ Game
→ Game Result
→ Series Resolution
→ Advancement
```

This follows the new competition specification, where phases are determined by the competing field and plots dynamically distribute players. The source competition notes explicitly define phases, plots, three-game advancement, and the one-hour match window.

# 4. Old → New Mapping

## 4.1 Season

### Current

```text
Season
```

### Target

```text
Season
├── ruleset
├── phases
└── competition configuration
```

### Action

**KEEP + EXTEND**

The existing `Season` remains the top-level competition container.

Do not create a new top-level Tournament object merely to support phases.

The Season already represents the correct lifecycle boundary.

### Existing fields that remain relevant

```text
id
league_id
name
description
status
start_date
end_date
registration_open_at
registration_close_at
```

### New responsibilities

Season becomes responsible for:

* competition ruleset reference;
* competition lifecycle;
* phase configuration;
* competition initialization;
* phase progression;
* final champion;
* competition completion.

### Important change

The existing:

```text
ACTIVE
PLAYOFFS
```

lifecycle should not be interpreted as the new Phase model.

A Phase is a competition-domain object inside an active season.

# 5. Division

## Current

```text
Season
└── Division
```

Division currently contains most of the competition configuration.

It also contains legacy assumptions around:

```text
ROUND_ROBIN_SINGLE
ROUND_ROBIN_DOUBLE
```

### Target

```text
Season
└── Division
    └── Competition
        ├── Phase
        ├── Plot
        └── Series
```

### Action

**KEEP + SIMPLIFY + EXTEND**

Division remains useful because the platform supports multiple divisions.

However, Division should stop being the place where the competition engine is hardcoded around round robin.

### Retire from competition logic

```text
CompetitionFormat.ROUND_ROBIN_SINGLE
CompetitionFormat.ROUND_ROBIN_DOUBLE
```

These should no longer control NGL's canonical competition generation.

They may be retained temporarily for migration compatibility, but new competition logic must not depend on them.

### New Division responsibilities

Division defines:

* participant pool;
* competition capacity;
* competition ruleset;
* competition configuration;
* active/inactive status.

The actual progression structure belongs to Phase.

# 14. Series Resolution

The current Match state machine cannot be used as the complete Series resolution engine.

The new flow is:

```text
Game 1
   ↓
Game 2
   ↓
Game 3
   ↓
Series Resolution
   ↓
Advance / Eliminate
```

### Normal result

```text
2–1
```

Winner advances.

### Draw rule

If **any Game is a draw**:

```text
Player A → ELIMINATED
Player B → ELIMINATED
Series → DUAL_ELIMINATION
```

This applies even if the other games would otherwise produce a 2–1 result.

### Unresolved Series

If the Series cannot produce a valid winner:

```text
Series → UNRESOLVED
Player A → ELIMINATED
Player B → ELIMINATED
```

This is a competition rule, not merely an operational Match status.

## New model

```text
Phase
```

This becomes the primary competition progression object.

### Responsibilities

A Phase defines:

* phase number;
* phase name;
* phase status;
* participant pool;
* plot count;
* plots;
* Series;
* duration;
* completion state;
* advancement state.

### Example

```text
Phase 1
Phase 2
Phase 3
Phase 4
...
```

The number of phases is determined dynamically by the competition field and actual advancement results.

# 16. Plot

## New model

```text
Plot
```

A Plot replaces the conceptual role previously played by a group or manually partitioned field.

### Responsibilities

A Plot defines:

* phase;
* plot number;
* participating players;
* Series generated within the plot.

### Important rule

A Plot does not have a fixed permanent capacity.

Its player count is determined by the available players in that Phase.

Therefore:

```text
Plot 1 = 20
Plot 2 = 20
Plot 3 = 20
Plot 4 = 20
Plot 5 = 20
```

may occur in Phase 1.

Then:

```text
Plot 1 = 10
Plot 2 = 12
Plot 3 = 12
```

may occur in Phase 2.

This is supported by the supplied competition model.

# 17. PhaseParticipant

A new Phase-specific participation record is required.

Conceptually:

```text
PhaseParticipant
```

It records:

```text
phase_id
player_id
source_phase_participant_id
seed
plot_id
status
outcome
advanced
eliminated
```

This is important because a player does not permanently belong to a Plot.

Instead:

```text
Phase 1
Player A → Plot 2
       ↓
wins Series
       ↓
Phase 2
Player A → Plot 1
```

Plot membership is therefore **phase-specific**.

# 18. Advancement

Advancement should not be inferred from standings.

It should be an explicit competition-domain operation.

Conceptually:

```text
SeriesResult
      ↓
SeriesResolution
      ↓
Advancement
      ↓
Next Phase Participant Pool
```

An advancement record should capture:

```text
source_series_id
player_id
source_phase_id
target_phase_id
outcome
created_at
```

This gives the system an auditable progression history.

# 21. Canonical Series Schedule

For a Series scheduled at `T`:

```text
T - 60 min
    Check-in opens

T - 30 min
    Check-in closes

T
    Series match window opens

T + 60 min
    Series match window closes

T + 90 min
    Results window closes
```

All three Games must occur inside:

```text
T → T + 60 minutes
```

The expected completed Game count is:

```text
3
```

This replaces the earlier scheduling model based on weekly scheduling periods and individual Fixture windows.

# 35. Data Ownership

```text
Season
    owns competition lifecycle

Division
    owns participant pool/configuration

    owns progression stage

Plot
    owns temporary phase grouping

Series
```

No object should infer another object's responsibilities merely because the old schema did so.

Implement:

```text

GameService

```

## Stage 3 — Build new APIs

Expose the new Phase/Plot/Series/Game domain.

## Stage 4 — Build new admin workspace

Replace Fixture-centric UI with Competition/Phase/Series UI.

## Stage 5 — Run Season 1 on new engine

The new engine becomes the authoritative competition system.

## Stage 6 — Retire legacy Fixture/Match engine

Only after:

* data migration is verified;
* E2E competition tests pass;
* Season 1 workflow is verified;
* no active process depends on legacy Fixture/Match generation.

# 40. Legacy Data Strategy

Existing records should not be silently deleted.

The migration should classify them as:

```text
LEGACY_ACTIVE
LEGACY_MIGRATED
LEGACY_ARCHIVED
```

Existing Season 1 data generated under the old Fixture model should be treated as legacy test/competition data unless explicitly migrated into the new competition model.

The new engine must not assume that an old Fixture can automatically become a valid Series.

A conversion is required because:

```text
Fixture
```

currently represents one player-v-player appointment,

while:

```text
Series
```

represents:

```text
3 Games
+
Series Result
+
Advancement
```

# 42. Canonical Development Principle

The most important implementation rule is:

> **Do not make the new Phase/Plot/Series/Game model a UI abstraction over the existing Fixture/Match schema.**

The new model must exist in the backend domain and database.

The API, admin UI, scheduling engine, result engine, advancement engine, audit system and notifications should all operate against the new domain.

The old Fixture/Match implementation becomes a migration source and compatibility layer during transition—not the hidden foundation underneath the new system.
